# OCR reliability dataset

This directory holds the inputs of the OCR reliability suite
(`backend/tests/reliability/ocr/test_ocr_reliability.py`):

```
dataset/
├── README.md                 ← this file
├── ground_truth.csv          ← what each image is expected to contain
├── images/                   ← the actual scanned/rendered images
│   ├── nia_clean_01.png
│   ├── ...
│   └── real_*.png            ← (your own real samples go here)
└── reports/                  ← per-run output (CSV + Markdown)
```

## What the suite does

For every row of `ground_truth.csv`, the test:

1. Loads the image from `images/<filename>`.
2. Runs OCR with the production engine (Tesseract by default).
3. Evaluates the result against four metrics:
   - **Exact match** (post-normalisation byte equality).
   - **Within Levenshtein budget** (1 char for IDs, 4 for names).
   - **Character accuracy** (`1 − distance / max_len`).
   - **Roster match** — feeds the OCR output to the production
     `match_student()` and checks the correct student is returned.
     This is the metric that matters in production: OCR can miss
     a couple of characters and the matcher still pulls out the
     right person via OCR-confusion tolerance and fuzzy name match.
4. Writes a per-sample CSV and a Markdown summary to `reports/`.
5. Optionally fails the test if any aggregate metric falls below an
   environment-controlled threshold.

## ground_truth.csv format

```csv
filename,expected_text,zone_type,style,noise,source
nia_clean_01.png,1234567,NIA,printed,no,synthetic
real_dni_uam_001.jpg,12345678A,DNI,handwriting,yes,real
```

| Column | Required | Allowed values |
|---|---|---|
| `filename` | yes | Any file under `images/` |
| `expected_text` | yes | Plain text, exact case |
| `zone_type` | yes | `NIA`, `DNI`, `NAME`, `TEXT`, `NUMBER` |
| `style` | no | `printed`, `handwriting`, `handwriting_sim`, ... |
| `noise` | no | `yes`, `no` |
| `source` | no | `synthetic`, `real`, free-form |

The `source` column is honoured by the synthetic regenerator: rows
with `source=synthetic` get rewritten on `generate_synthetic`; rows
with any other value are preserved.

## Default synthetic dataset (out of the box)

The repo ships six synthetic images so the test runs with no manual
setup. They are generated by:

```bash
python -m tests.reliability.ocr.generate_synthetic
```

These synthetics are just plumbing — printed text rendered with PIL,
maybe with light noise. They prove the pipeline works; they do **not**
give you a defensible reliability number, because no scanned student
sheet looks like that. Replace them with real samples for the TFG
defence.

## How to obtain a real dataset

Putting together a real OCR dataset for handwritten Spanish IDs takes
some legwork because none of the public OCR benchmarks target this
exact distribution (Spanish DNI/NIA writing on exam covers).
Practical paths, in rough order of effort:

### 1. Mock-scan your own (fastest, ~2 hours)

- Print a blank cover sheet with three labelled boxes: **NIA**,
  **DNI** (8 digits + 1 letter), **Nombre**.
- Recruit 8–12 friends, classmates, family. Each fills out the boxes
  with a pen of their choice. They are the "students".
- Scan everything at 300 DPI on the EPS scanner (or use a phone app
  like Microsoft Lens / CamScanner with shadow correction).
- Crop each image to one zone (you can do this manually in
  Preview / GIMP, or write a quick PIL script).
- Generate `ground_truth.csv` with the actual text each person wrote.
- Result: ~30 cropped images, fully under your control, GDPR-clean if
  you ask consent.

This is **what I'd do for a TFG defence** — small, real, defensible.

### 2. UAM volunteer round (more representative, but slower)

If you have 1–2 weeks of slack, run a "data day" in a UAM hallway:
ask 30+ people to fill the same form. The handwriting variety
(students from different countries, age groups) is exactly the
distribution your system will face in production. Same flow as #1
but with 100+ samples.

### 3. Public handwritten-text datasets (no Spanish-specific ones, but useful for raw OCR sanity)

These are not Spanish IDs but they exercise the same OCR engines:

- **IAM Handwriting Database** —
  <https://fki.tic.heia-fr.ch/databases/iam-handwriting-database>.
  English handwriting, freely available for research. Useful as a
  sanity dataset for the `NAME` zone type if you are happy with
  English-only names.
- **MNIST / EMNIST** — <https://www.nist.gov/itl/products-and-services/emnist-dataset>.
  Single-character handwritten digits + letters. Don't use them for
  whole-NIA recognition (no compositional context) but they are
  useful if you want to break down failures by character.
- **IFN/ENIT** — Arabic handwriting, not relevant here, mentioned to
  rule it out.

### 4. Public Spanish text datasets (printed, not handwritten — but free Spanish coverage)

- **Spanish IIIT-CFW** and similar synthetic-Spanish OCR corpora,
  found on Kaggle and Hugging Face. Search "spanish ocr handwritten"
  or "spanish DNI OCR". As of 2026 there is no canonical, large,
  Spanish-handwritten-DNI corpus (privacy is the main reason).

### 5. Generate synthetic Spanish handwriting (last resort)

If you cannot scan real samples, look at:

- **TRDG** (`pip install trdg`) — generates synthetic OCR datasets
  with TrueType fonts. Produces *printed* text on noisy backgrounds;
  not handwriting, but you can mix in handwriting fonts (DejaVu Sans
  has a few handwriting-like Italic faces; "Caveat", "Just Another
  Hand", "Indie Flower" via Google Fonts are widely used).
- **DiffusionOCR / synthetic handwriting models** — newer projects;
  expensive to set up but produce convincing fake handwriting.

The current `generate_synthetic.py` already does a poor-man's
version of this (italic font + small jitter). It's meant to keep
the suite green in CI, not to give you real numbers.

### Privacy note

If you collect real samples:

- Get **explicit consent** in writing — a one-line "I authorise the
  use of this image and the data on it for academic OCR testing"
  is enough.
- Do **not** commit images of real DNIs to the repo. Either commit
  cropped name boxes only, or store the image set outside git and
  load it by path. The CSV format supports any filename, so a
  per-developer dataset directory is trivial.

## How to run the suite

```bash
# Default: Tesseract, Spanish, no thresholds.
pytest tests/reliability/ocr/test_ocr_reliability.py -v -s

# Tesseract on systems where the trained data uses ISO 639-2:
SCDEE_OCR_LANGUAGE=spa pytest tests/reliability/ocr/test_ocr_reliability.py -s

# EasyOCR (downloads ~100 MB on first run):
SCDEE_OCR_ENGINE=easyocr pytest tests/reliability/ocr/test_ocr_reliability.py -s

# Enforce minimums in CI once you have a stable dataset:
SCDEE_OCR_MIN_EXACT=0.7 \
SCDEE_OCR_MIN_ROSTER=0.95 \
pytest tests/reliability/ocr/test_ocr_reliability.py -s
```

## How to add new samples

1. Drop your image into `images/`.
2. Append a row to `ground_truth.csv` with `source=real` (or any
   value other than `synthetic`).
3. Re-run the suite. The new sample shows up in the next report.

If you re-run `python -m tests.reliability.ocr.generate_synthetic`,
your real rows are preserved (they are filtered by `source !=
synthetic`).

## Reading the reports

Every test run writes one CSV and one Markdown file under
`reports/`, named `ocr_reliability_<engine>_<UTC timestamp>.{csv,md}`.

The Markdown file is meant to be the artefact you screenshot for the
TFG defence. The CSV is for further processing (ggplot, pandas,
spreadsheets).
